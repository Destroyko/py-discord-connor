# Anti (анти-работяга)

## Назначение
На сервере есть роль **"работяга"**. Без неё у пользователя нет доступа к части чатов и нет возможности отправлять медиафайлы в принципе. Компонент `anti` - это "чёрный список" (внутренняя БД бота), позволяющий модератору лишить конкретного пользователя права снова получить роль "работяга" самостоятельно (через `!give`/`/give`), даже если роль у него забрали.

Статус "анти-работяги" даёт более широкие последствия, чем просто отсутствие роли "работяга":
- нет доступа к отправке медиафайлов;
- нет разрешения стримить в голосовых комнатах;
- нет права **отправлять сообщения** в чат **"предложка"** (право видеть канал и читать историю не трогается), даже если у пользователя есть роль, которая обычно даёт доступ туда писать - см. отдельный механизм точечного запрета в [check.md](check.md).

## Команды
| Команда | Алиасы | Кто вызывает | Действие |
|---|---|---|---|
| `/add target:<id> reason:[опционально]` | `!add <id> [reason]` | Модератор | Добавляет пользователя (по ID) в список "анти-работяг" с причиной (опционально) и забирает роль "работяга", если она у него была |
| `/del target:<id> reason:[опционально]` | `!del <id> [reason]` | Модератор | Убирает пользователя из списка "анти-работяг" (причина опциональна) и возвращает роль "работяга" |

Именование параметров `target`/`reason` - общая конвенция для всех slash-команд бота, см. [base.md](../base.md) "Команды - общие конвенции".

Примеры:
```
!add 758355933230530621 п11 с медиа
!del 772416347111555082 отсидел
```

## Логика работы
1. Модератор вызывает `/add <id> [reason]` (или `!add <id> [reason]`) на пользователе-нарушителе. Причина опциональна. Если `id`/упоминание невалидно или не резолвится ни в какого пользователя Discord - отказ: `Укажите пользователя или id` (тот же текст, что и в аналогичном случае у [mute.md](mute.md)/[banKick.md](banKick.md)).
2. Если пользователь **уже в анти-списке** - команда отклоняется с ошибкой `Пользователь @упоминание уже существует в списке антиработяг`.
3. Бот:
   - добавляет ID пользователя во внутренний список "анти-работяг" вместе с причиной и датой (персистентно, БД);
   - **не трогает** права в "предложке" на этом этапе - запрет туда ставится лениво, только по факту нарушения, см. [check.md](check.md);
   - отправляет в `#антиработяги` **два отдельных сообщения**:
     1. Embed **"Добавление"**:
        - `Пользователь @упоминание добавлен в список антиработяг`
        - **Причина**: указанный текст причины
        - **Дата добавления**: `ДД-ММ-ГГГГ ЧЧ:ММ:СС`
        - footer: захардкоженный текст `Claptrap желает вам приятного дня` + таймстемп (например: `Claptrap желает вам приятного дня • 16-08-2026 18:49`) - не пул со случайным выбором, одна фиксированная строка; при желании меняется вручную в коде, превращать в пул на первую реализацию не нужно
     2. Результат попытки забрать роль "работяга" (если она была у пользователя) - прямой ответ самой команды `/add` (не через наблюдение за ручными изменениями, см. ниже):
        - при успехе: `@упоминание` / **изъяли роль** / `Работяга` / `Подробности в журнале аудита.` / `Добавить в список антиработяг можно через команду` / `!add id/квот причина`; без указания author'а (действие уже видно из соседнего embed'а "Добавление");
        - при неудаче (пользователь не найден на сервере или роли у него не было) - текст: `Я не смог изъять роль так как пользователь не найден или не имеет такой роли`.
4. Пока пользователь в списке - при попытке самостоятельно получить роль "работяга" командой `!give` (в специальном чате для самовыдачи роли, см. [roleGiver.md](roleGiver.md)) бот сверяется со списком анти-работяг и **отказывает** в выдаче с текстом `Вам отказано в выдаче роли. Вы можете связаться с любым модератором в чате или через личные сообщения для апелляции.` (см. сценарий 3 в roleGiver.md). Статус анти-работяги хранится в БД бота и **не зависит от членства на сервере** - если пользователь выйдет и зайдёт даже через год, `!give` всё равно откажет мгновенно, пока его явно не удалят из списка через `/del`. `!give` - единственный путь получить роль "работяга"; других путей (реакция, авто-роль при входе) не предусмотрено.
5. Модератор вызывает `/del <id> [reason]` (или `!del <id> [reason]`), чтобы снять ограничение (причина опциональна, как у `/add`). Если `id`/упоминание невалидно или не резолвится ни в какого пользователя Discord - тот же отказ, что и у `/add`: `Укажите пользователя или id`.
   - **Особый случай - удалённый аккаунт Discord**: запись в анти-списке может быть очень старой, а сам аккаунт к этому моменту удалён на стороне Discord целиком (не просто вышел с сервера - id вообще ни во что не резолвится). Это тоже попадает под "не резолвится" выше - бот отвечает тем же текстом `Укажите пользователя или id`, но **дополнительно**, раз id всё равно значится в БД анти-списка, тихо удаляет эту запись из БД (без отдельного уведомления об этой очистке) - чтобы не оставлять в списке ссылку на аккаунт, который больше никогда не резолвится.
   - пользователь удаляется из списка "анти-работяг";
   - роль "работяга" возвращается **безусловно** - независимо от того, была ли она у пользователя на момент `/add`;
   - **если ранее ботом был выставлен deny-overwrite в "предложке" для этого пользователя** (см. [check.md](check.md)) - бот сразу же пытается его снять в рамках этой же команды (без ожидания следующего `!check`);
   - бот отправляет **два отдельных сообщения**:
     1. Embed **"Удаление"**: `Пользователь @упоминание удалён из списка антиработяг`, **Причина**: текст причины, footer - тот же захардкоженный текст + таймстемп. Поля "Дата удаления" нет (в отличие от "Дата добавления" в embed'е "Добавление").
     2. Обычное текстовое сообщение (не embed): `Роль возвращена`.
6. Если модератор снимает роль "работяга" вручную через Discord UI (не через `/add`) - в `#антиработяги` команда-эхо не появляется (это не вызов команды), но бот всё равно ловит это как отдельное событие и публикует уведомление "изъяли роль" с указанием автора действия по журналу аудита Discord - см. "Наблюдение за ручными изменениями роли" ниже.
7. Если модератор выдаёт роль "работяга" вручную через Discord UI (не через `/give`/ручное одобрение в roleGiver):
   - если пользователь **не** в анти-списке - бот **ничего не пишет** в `#антиработяги` (не событие для бота);
   - если пользователь **в анти-списке** на момент выдачи - пользователь автоматически убирается из анти-списка, и генерируется запись в `#антиработяги` по аналогии с логом `/del` (обнаруживается тем же механизмом наблюдения, что и снятие роли вручную выше - см. "Наблюдение за ручными изменениями роли" ниже, только для события выдачи роли, не снятия).

## Наблюдение за ручными изменениями роли (вне команд бота)
Отдельный механизм внутри `anti` (не завязан на вызов команды): слушает само событие изменения роли "работяга" в Discord (`on_member_update`/аналог), чтобы не терять из виду действия, сделанные модератором напрямую через Discord UI, в обход `/add`/`/del`.

**Замечание к реализации**: снятие роли ботом внутри `/add` и снятие роли вручную через Discord UI порождают одно и то же Discord-событие `on_member_update` - реализация должна отличать "снял бот сам, только что, в рамках своей же команды" от "снял кто-то через UI", чтобы не сработать дважды (иначе на один `/add` придёт два уведомления вместо одного).

### Снятие роли вручную
Модератор снимает роль "работяга" через Discord UI, без вызова `/add`. Бот ловит событие, ищет ответственного через журнал аудита Discord (см. "Поиск ответственного по журналу аудита" ниже) и публикует в `#антиработяги`:
```
@упоминание
изъяли роль
Работяга

Подробности в журнале аудита.
Добавить в список антиработяг можно через команду !add id/квот причина
```
author embed'а = найденный по audit log модератор (имя + аватар). Формат текста идентичен тому, что `/add` публикует сам от себя при успешном снятии роли (см. "Логика работы" выше, п.3) - совпадение сделано намеренно, различается только источник (сама команда vs пассивное наблюдение) и наличие author'а.

Срабатывает независимо от анти-статуса цели - даже если пользователь никогда не был в анти-списке (просто имел роль "работяга" и её сняли вручную), уведомление всё равно публикуется. Условие "состоит в анти-списке" относится только к зеркальной механике выдачи роли (см. ниже), не к снятию.

### Выдача роли вручную (зеркальная механика, только для анти-работяг)
- Если роль "работяга" выдана пользователю, который на момент выдачи состоит в анти-списке, вручную через Discord UI (не через `/give`) - пользователь автоматически убирается из анти-списка, генерируется запись в `#антиработяги` по аналогии с логом `/del` (см. "Логика работы" выше, п.5).
- Если пользователь не в анти-списке - ручная выдача роли не событие для бота, ничего не логируется (обычный случай, не отслеживается). Это касается и тех, кому до этого вручную снимали роль (см. выше): раз он не попал в анти-список, повторная ручная выдача роли тоже проходит тихо, без записи.

### Поиск ответственного по журналу аудита
После ручного изменения роли в журнале аудита Discord появляется запись вида "{модератор} обновляет роли у {пользователь}" с указанием конкретного действия ("Убирает роль" / "Добавляет роль" - "Работяга") - запись становится доступна через API примерно через **4–5 секунд** после самого события. Бот должен запросить журнал аудита с этой задержкой и найти запись, у которой цель (target) совпадает с пользователем из события `on_member_update`; автор записи - и есть искомый ответственный модератор.

## Обработка ошибок (точные тексты)
| Ситуация | Ответ бота |
|---|---|
| `id`/упоминание невалидно или не резолвится, при `/add` или `/del` | `Укажите пользователя или id` |
| `/add` на пользователе, который уже в анти-списке | `Пользователь @упоминание уже существует в списке антиработяг` |
| Не удалось изъять роль "работяга" при `/add` (пользователь не найден на сервере или роли не было) | `Я не смог изъять роль так как пользователь не найден или не имеет такой роли` |

## Хранимые данные
- Список ID пользователей в статусе "анти-работяга", с причиной и датой добавления - постоянное хранилище (БД), переживает рестарт бота.

## Логирование
- `/add`/`/del` - прямой embed-ответ в `#антиработяги` (отдельный от `#бот-команды` и от каналов `!give`, см. [base.md](../base.md) "Каналы, завязанные на бота"), плюс сообщение о результате ручного/автоматического возврата роли.
- В канал заявок `!give`/канал логов решений по `!give` (см. "Логирование" в [roleGiver.md](roleGiver.md)) `/add`/`/del` **не** дублируются.
