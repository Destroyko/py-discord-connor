# EventWatcher — логирование действий (п.6 из base.md)

## Назначение
Две отдельные задачи, обе с итогом в виде записи в канале:
1. **Пассивное** отслеживание изменений роли "работяга", сделанных **не через команды бота** (вручную через Discord UI), с определением ответственного через журнал аудита Discord.
2. Логирование решений модератора по заявкам `!give` (одобрение/отказ), см. ниже.

Важно: когда роль "работяга" снимается **самим ботом как следствие вызова `/add`**, соответствующее сообщение — это прямой ответ команды `/add` (см. [anti.md](anti.md)), а не отдельное срабатывание eventWatcher. eventWatcher занимается только случаем, когда снятие/выдача роли произошло **в обход бота**, т.е. вручную через Discord UI.

## Каналы
Три разных канала (все три ID бот обязан знать в `.env`, см. [base.md](../base.md) "Каналы, завязанные на бота"):
1. **`#антиработяги`** (тот же, где отвечают `/add`/`/del`, см. [anti.md](anti.md); отдельный от `#бот-команды`) — сюда же падают уведомления о ручном (не через `/add`) снятии/выдаче роли "работяга".
2. **`#реквесты-работяг`** — сюда roleGiver публикует `@here`-запросы с реакциями ✅/❌ на ручную проверку, см. [roleGiver.md](roleGiver.md). Не входит в зону ответственности eventWatcher — это канал самого roleGiver.
3. **`#аудит`** — сюда eventWatcher публикует результат каждого решения модератора по заявке `!give` (см. ниже), отдельно от канала заявок (п.2).

## Механика: пассивное отслеживание ручного изменения роли "Работяга"
Не привязано к команде — срабатывает на **само событие изменения роли** (Discord `on_member_update`/аналог), только когда изменение сделано **не через `/add`/`/del`/`/give`**.

**Замечание к реализации**: снятие роли ботом внутри `/add` и снятие роли вручную через Discord UI порождают одно и то же Discord-событие `on_member_update` — реализация должна отличать "снял бот сам, только что, в рамках своей же команды" от "снял кто-то через UI", чтобы не сработать дважды (иначе на один `/add` придёт два уведомления вместо одного).

### Снятие роли вручную
Модератор снимает роль "работяга" через Discord UI, без вызова `/add`. Бот ловит событие, ищет ответственного через **журнал аудита Discord** (audit log) и публикует в `#антиработяги`:
```
@упоминание
изъяли роль
Работяга

Подробности в журнале аудита.
Добавить в список антиработяг можно через команду !add id/квот причина
```
author embed'а = найденный по audit log модератор (имя + аватар). Формат текста идентичен тому, что `/add` публикует сам от себя при успешном снятии роли (см. [anti.md](anti.md)) — совпадение сделано намеренно, различается только источник (сама команда vs пассивное наблюдение) и наличие author'а.

**Подтверждено тестом на живом сервере**: срабатывает **независимо от анти-статуса** цели — даже если пользователь никогда не был в анти-списке (просто имел роль "работяга" и её сняли вручную), уведомление всё равно публикуется. Условие "состоит в анти-списке" относится только к зеркальной механике выдачи роли (см. ниже), не к снятию.

### Выдача роли вручную (зеркальная механика, только для анти-работяг)
- Если роль "работяга" выдана пользователю, который **на момент выдачи состоит в анти-списке** ([anti.md](anti.md)), вручную через Discord UI (не через `/give`) — пользователь автоматически убирается из анти-списка, генерируется запись в `#антиработяги` по аналогии с логом `/del` (см. [anti.md](anti.md)).
- Если пользователь **не** в анти-списке — ручная выдача роли не событие для бота, ничего не логируется (обычный случай, не отслеживается). **Подтверждено тестом**: даже если этому пользователю до этого вручную снимали роль (см. выше) — раз он не попал в анти-список, повторная ручная выдача роли тоже проходит тихо, без записи.

## Механика: логирование решений по `!give`
В `#аудит` (отдельном от `#реквесты-работяг`) на каждое решение модератора (✅/❌ на заявку ручной проверки, см. [roleGiver.md](roleGiver.md)) публикуется embed:
- author = модератор, принявший решение (имя + аватар);
- цвет полосы слева: **зелёный** — одобрено, **красный** — отказано;
- текст:
  - одобрено: `{модератор} обновил {упоминание цели}` / `Выдана роль` / `@Работяга`
  - отказано: `{модератор} отказал {упоминание цели}` / `Отказ в выдаче роли` / `@Работяга`

## Поиск ответственного по журналу аудита
Подтверждено (проверено на живом сервере): после ручного изменения роли в журнале аудита Discord появляется запись вида "{модератор} обновляет роли у {пользователь}" с указанием конкретного действия ("Убирает роль" / "Добавляет роль" — "Работяга") — запись становится доступна через API примерно через **4–5 секунд** после самого события. Бот должен запросить журнал аудита с этой задержкой и найти запись, у которой цель (target) совпадает с пользователем из события `on_member_update`; автор записи — и есть искомый ответственный модератор.
