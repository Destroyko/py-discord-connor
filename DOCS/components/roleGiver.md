# RoleGiver - выдача/снятие роли "работяга"

## Назначение
Самостоятельное получение базовой роли "работяга" новыми участниками через команду в спец. чате, с автоматической проверкой на подозрительность аккаунта (анти-твинк) и на статус "анти-работяга" ([anti.md](anti.md)), плюс запасной контур ручного решения модератором через реакции.

## Канал
**`#выдача-работяг`** (топик: "Для получения работяг, напишите в чат команду !give") - единственное место, где вызывается `!give`/`/give`. Доступ к этому каналу привязан к **отсутствию** роли "работяга" - как только роль получена, пользователь теряет доступ к каналу (настройка видимости канала на стороне Discord, не бот). Из этого следует, что сценарий "пользователь уже имеет роль и вызывает `!give` повторно" на практике исключён на уровне доступа к каналу, не проверкой в коде бота.

Плюс отдельный **`#реквесты-работяг`** только для модераторов, куда падают запросы на ручную обработку с пингом `@here`. Это не тот же канал, что `#аудит` - туда результат решения модератора логируется отдельно, см. "Логирование" ниже. См. [base.md](../base.md) "Каналы, завязанные на бота" - полный список отдельных каналов кластера "работяга".

## Команда
`!give` / `/give` - без аргументов. Действует на самого вызывающего (сам себе запрашивает роль).

## Логика работы
При вызове `!give` бот проверяет пользователя и выбирает один из трёх сценариев:

### 1. Чистый аккаунт → мгновенная выдача
Условие: пользователь **не** в анти-списке ([anti.md](anti.md)) И аккаунт **не выглядит подозрительно молодым**.
→ Роль выдаётся сразу, ответ бота: `Роль выдана.`

### 2. Подозрительно новый аккаунт → ручная обработка
Условие: пользователь не в анти-списке, И срабатывает **хотя бы одно** (ИЛИ, не И) из двух условий:
   - **B.** сам Discord-аккаунт "новорег" - с момента его регистрации в Discord (а не входа на сервер) прошло **меньше 6 месяцев**, независимо от даты входа на этот конкретный сервер;
   - **C.** пользователь находится на сервере меньше 2 недель (с момента входа, независимо от возраста аккаунта).

Оба условия - независимые обязательные проверки ("в любом случае должен просидеть 2 недели" + "всегда смотрим на возраст аккаунта"), не взаимоисключающие альтернативы - оба участвуют в OR.

Условия не взаимоисключающие - если сработало несколько сразу, в сообщении перечисляются все причины (см. пример ниже).

→ Бот отвечает пользователю в `#выдача-работяг`:
   ```
   Ваш запрос передан на ручную обработку. С Вами свяжутся при необходимости.
   ```
→ Параллельно бот пишет в `#реквесты-работяг` (с `@here`; если у бота в этом канале нет права "Упоминать всех" - `@here` уйдёт обычным неактивным текстом, без реального оповещения, это осознанно допустимо), перечисляя все сработавшие причины отдельными строками:
   ```
   @here Пользователь @упоминание запросил работягу. Причины, по которым я не выдал:
   Новорег. Дата регистрации: 13.12.25 19:21:36
   Аккаунт находится на сервере менее 2х недель.
   Дата присоединения: 20.08.26 14:53:38
   ```
   (в примере сработали одновременно B и C; в других случаях может быть только одна строка причины - например, только C: `Аккаунт находится на сервере менее 2х недель.` + `Дата присоединения: ...`)

   Под сообщением - 2 реакции для решения модератора: ✅ и ❌ (третья иконка на скриншотах - стандартная кнопка Discord "добавить реакцию", не реакция бота).

   Пользователь может вызвать `!give` повторно, пока предыдущий запрос ещё висит на ручной обработке - спам-защиты/блокировки повторного запроса нет, уходит новый независимый запрос.

   Если ни один модератор не отреагирует - заявка **висит бессрочно**, никакого тайм-аута или эскалации нет. Если отреагируют **несколько модераторов** почти одновременно (гонка ✅/❌) - побеждает **первая** по времени реакция, остальные игнорируются.

→ Модератор реагирует:
   - **✅** - бот выдаёт роль, удаляет своё сообщение в `#реквесты-работяг`, пишет в `#выдача-работяг`:
     ```
     @упоминание, роль выдана.
     ```
   - **❌** - бот удаляет своё сообщение в `#реквесты-работяг`, пишет в `#выдача-работяг`:
     ```
     @упоминание, Вам отказано в выдаче роли. Вы можете связаться с любым модератором в чате или через личные сообщения для апелляции.
     ```

### 3. Анти-работяга → мгновенный отказ
Условие: пользователь есть в анти-списке ([anti.md](anti.md)).
→ Бот сразу отказывает, **без** дополнительных сообщений в `#реквесты-работяг` (в отличие от сценария 2).
→ Текст отказа - тот же, что в сценарии 2 после ❌: `Вам отказано в выдаче роли. Вы можете связаться с любым модератором в чате или через личные сообщения для апелляции.`

## Логирование
На каждое решение модератора (✅/❌ на заявку ручной проверки, см. сценарий 2 выше) `roleGiver` публикует в **`#аудит`** (отдельном от `#реквесты-работяг`) embed:
- author = модератор, принявший решение (имя + аватар);
- цвет полосы слева: **зелёный** - одобрено, **красный** - отказано;
- текст:
  - одобрено: `{модератор} обновил {упоминание цели}` / `Выдана роль` / `@Работяга`
  - отказано: `{модератор} отказал {упоминание цели}` / `Отказ в выдаче роли` / `@Работяга`

Сценарий 1 (мгновенная выдача) и сценарий 3 (мгновенный отказ анти-работяге) - не решение модератора, в `#аудит` не логируются.

## Хранимые данные
- Анти-список - общий с [anti.md](anti.md).
- Состояние "запрос на ручной проверке" (message ID в `#реквесты-работяг` → id пользователя-запросившего) - **должно храниться персистентно в БД**, не только в памяти. Заявки могут висеть сутки и дольше в ожидании реакции модератора (см. [environment.md](../environment.md) - "Развёртывание и устойчивость к рестарту"), и бот обязан корректно обработать реакцию, поставленную уже после его рестарта.
- Технически это означает обработку реакций через "сырые" события (например, `on_raw_reaction_add` в discord.py - работает и для сообщений, отсутствующих в кеше клиента после рестарта), не через события, зависящие от внутреннего message-кеша бота.
