# Требования к реализации (разработка)

> Архитектурный уровень: как код должен быть построен (тестируемость, самодиагностика, логирование). Что делает каждый модуль - см. [base.md](base.md), [components/*.md](components/) и сквозные правила в [rules.md](rules.md). Стек, права бота на сервере, устойчивость к рестарту и структура конфигурации - среда - см. [environment.md](environment.md).

## Тестирование

Юнит-тестами обязательно покрывается вся логика, не зависящая напрямую от сети/Discord API:
- парсинг и валидация времени мьюта, диапазон `60s–28d`, формат `<число><суффикс>` без составных форматов ([mute.md](components/mute.md));
- проверка иерархии ролей (позиция цели vs инициатора, цель - бот, явная проверка `target.id == guild.owner_id`) - общая утилита из [rules.md](rules.md) "Роли и права";
- выбор сценария `!give` (чистый / ручная проверка / анти-работяга) по условиям B (новорег < 6 мес.) и C (< 2 недель на сервере), обе - OR ([roleGiver.md](components/roleGiver.md));
- тик начисления опыта в Voices: пропуск тика при отсутствии владельца в своей комнате, исключение гостя (deaf/бот), +8/+10 за гостя, +5 бонус за стрим при ≥1 учтённом госте ([Voices.md](components/Voices.md));
- лимит 100 записей личного бан-листа ([Voices.md](components/Voices.md));
- мягкий лимит 300 и граница 14 дней в `!purge` ([purge.md](components/purge.md));
- разбор ответа Command Permissions API и порядок приоритета `default_member_permissions` → роли → каналы (канал побеждает) - см. "Command Permissions API" ниже.

Требование к коду: перечисленная логика должна быть выделена в чистые функции/классы, принимающие примитивы или простые dataclass'ы - не требовать на входе реальный `discord.Guild`/`discord.Member`/`discord.Role`, чтобы не мокать всю библиотеку ради теста одного правила.

Discord-специфичные вызовы (создание канала, выдача роли, отправка embed, timeout) - тестируются моками (`unittest.mock`) или через `dpytest`, не реальными вызовами к Discord API ни в юнит-, ни в CI-тестах.

Реальная проверка прав/доступов в самом Discord - не задача тестов, это задача стартовой диагностики (см. ниже).

Тесты обязаны проходить до деплоя - это gate пайплайна, деплой без прогона тестов не допускается.

## Стартовая диагностика (preflight)

При старте бота, сразу после подключения к гильдии и до перехода в режим обычной обработки событий/команд, бот проверяет собственное окружение и выводит результат в лог построчно, по одной проверке на строку, с единым префиксом `[startup][<раздел>]`, чтобы искать по логам (`journalctl`) конкретный этап.

Пример:
```
[startup] Гильдия: OK (ID совпадает)
[startup] Intents: OK (Guild Members, Message Content включены)
[startup][роли] "работяга" (123456789012345678): OK, бот выше в иерархии
[startup][роли] "Молчун": OK
[startup][роли] "Душа компании": ОШИБКА - роль не найдена по ID из .env
[startup][каналы] #реквесты-работяг: OK (View, Send Messages, Add Reactions, Mention Everyone)
[startup][каналы] #аудит: ОШИБКА - не хватает права "Send Messages"
[startup][категория] "роддом": OK
[startup][БД] Подключение: OK
[startup][Command Permissions API] Доступ: OK
[startup] ИТОГ: 2 ошибки - "Душа компании" не будет переустанавливаться (Voices), лог по !give в #аудит не будет писаться (roleGiver). Остальной функционал поднят.
```

Каждая строка при ошибке называет **конкретную причину** (какой роли/права/канала не хватает); обобщённые сообщения вроде "insufficient permissions" недопустимы - диагностика в логе должна быть отличима от голого исключения библиотеки.

### Что проверяется

**Базовое** (блокирует полный запуск бота при провале - процесс завершается с ненулевым кодом, не переходит в режим ожидания команд):
- бот подключился именно к гильдии из `.env` (совпадение ID);
- privileged intents (Guild Members, Message Content) реально включены - если нет, gateway отклоняет соединение с непрозрачной для оператора ошибкой библиотеки; бот обязан явно поймать и залогировать это как отдельную причину;
- подключение к БД установлено, схема/миграции применены.

**Роли, которыми бот управляет** ("работяга", "Молчун", "Душа компании") - при провале конкретная роль/связанная команда отключается с логом, бот в целом поднимается:
- ID роли резолвится (`guild.get_role(id)` не `None`);
- позиция роли бота (`guild.me.top_role.position`) выше позиции каждой из управляемых ролей - иначе Discord API откажет в выдаче/снятии независимо от того, какие права выданы боту (даже гипотетический `Administrator` не отменяет это конкретное правило иерархии для управления ролями - но у бота его в любом случае нет, см. [rules.md](rules.md) "Роли и права").

**Права уровня сервера** (guild-level permissions) - при отсутствии конкретного права отключается только связанный с ним функционал. Курируемый список прав, реально выданных роли бота на сервере, зафиксирован в [environment.md](environment.md) "Права бота на сервере" - таблица ниже не должна требовать ничего сверх него:

| Право | Нужно для | Модуль |
|---|---|---|
| Ban Members | `/ban`, `/unban` | banKick |
| Kick Members | `/kick` | banKick |
| Moderate Members (timeout) | `/mute`, `/unmute` | mute |
| Manage Roles | выдача/снятие "работяга"/"Молчун"/"Душа компании" | roleGiver, anti, mute, Voices |
| Manage Channels | per-user overwrite на приватных войсах, deny-overwrite в "предложке" | Voices, check |
| Manage Messages | `!purge`, удаление сообщения при простановке overwrite в "предложке" | purge, check |
| View Audit Log | поиск ответственного модератора при ручном изменении роли | anti |
| Move Members | перемещение пользователя из канала-триггера в новую комнату | Voices |
| Manage Server | пауза инвайтов (`invites_disabled_until`) - понадобится, только если `/anti-bot` войдёт в скоуп реализации, см. [antiBot.md](components/antiBot.md) | antiBot (вне скоупа) |

**Права по конкретным каналам** (`channel.permissions_for(guild.me)`, не общий список прав сервера - оверрайты канала могут урезать права бота на конкретном канале даже в пределах того, что выдано на уровне сервера):

| Канал | Нужные права | Модуль |
|---|---|---|
| `#реквесты-работяг` | View, Send Messages, Add Reactions, Mention Everyone (`@here`) | roleGiver |
| `#бот-команды` | View, Send Messages, Embed Links | mute, banKick, purge, Voices |
| `#антиработяги` | View, Send Messages, Embed Links | anti |
| `#аудит` | View, Send Messages, Embed Links | roleGiver |
| `#выдача-работяг` | View, Send Messages | roleGiver |
| `#баны` | View, Send Messages, Embed Links | banKick |
| `#чек-лист` | View, Send Messages, Embed Links | moderationChat |
| `#чек-лист2` | View, Send Messages, Embed Links | moderationChat |
| `#флудиславль` | View, Send Messages, Embed Links (для `/ladder`) | check, Voices |
| `#предложка` | View, Manage Messages (удаление сообщения нарушителя), Manage Channels (простановка/снятие per-user deny-overwrite) | check |
| категория "роддом" | View (на сами каналы внутри, для скана `!purge`/чек-листов) | moderationChat, purge |
| категория приватных войс-комнат | View, Manage Channels, Move Members (создание комнаты и перемещение владельца внутрь) | Voices |

**Command Permissions API** - Discord фильтрует по Command Permissions только сам `/`-путь; на `!`-путь (обычные текстовые сообщения) эта фильтрация не распространяется - если она нужна и там (см. [rules.md](rules.md) "Роли и права"), бот обязан реплицировать её сам:
- Discord отдаёт эту конфигурацию через API - `GET /applications/{application_id}/guilds/{guild_id}/commands/permissions` (работает на обычном bot-токене), и присылает live-обновления через gateway-событие `APPLICATION_COMMAND_PERMISSIONS_UPDATE` при каждом изменении на сервере. Бот вычитывает эту конфигурацию при старте, держит в кэше, обновляемом по этому событию, и на её основе сам проверяет `!`-вызовы - воспроизводя тот же приоритет, что использует сам Discord: базовое требование команды (`default_member_permissions`) → оверрайды по ролям → оверрайды по каналам (канал побеждает).
- При недоступности API на старте (ошибка запроса) префиксные (`!`) команды обязаны быть **отключены полностью** (fail closed), пока кэш не будет успешно прогружен - недопустимо оставлять `!`-путь работающим без реплики ограничений, которые Discord применяет к `/`-пути.

### Ручной перезапуск проверки без рестарта бота - команда `/healthcheck`
`/healthcheck` - без аргументов, только slash-вариант (без `!healthcheck`). Доступ к вызову - как у любой slash-команды бота, через штатные Discord Command Permissions (роли + каналы), без отдельной проверки роли в коде, см. [rules.md](rules.md) "Роли и права". Ответ **ephemeral** - виден только вызвавшему.

Назначение: посмотреть состояние прав/каналов бота прямо из Discord, не заходя на VPS и не читая `journalctl` - модератор без доступа к серверу должен получить тот же диагностический отчёт, что попадает в лог при старте.

В дополнение к построчному отчёту preflight-проверок (см. пример выше) ответ на `/healthcheck` включает **аптайм** - время, прошедшее с момента последнего фактического запуска процесса (`on_ready`), например `Аптайм: 4д 3ч 12м`. Отсчитывается от старта текущего процесса в памяти, не персистентно - рестарт обнуляет счётчик, в этом и смысл поля.

Стартовая диагностика и `/healthcheck` - это **один и тот же код**: единая функция `run_preflight_checks(guild) -> list[CheckResult]`, которую вызывает и `on_ready`, и хендлер команды. Отдельной реализации "команда сама себя проверяет" нет - она просто вызывает ту же функцию заново.

Рестарт для этого не нужен, потому что бо́льшая часть проверок читает не статичный снимок, а **живое состояние**, которое discord.py и так держит в памяти актуальным через gateway-события - роли, каналы, permission-оверрайты обновляются в кэше сразу же при изменении на сервере (`GUILD_ROLE_UPDATE`, `CHANNEL_UPDATE` и т.п.), без отдельного опроса. Поэтому:
- проверки ролей/каналов/иерархии (`guild.get_role`, `channel.permissions_for(guild.me)`, позиция роли бота) - просто читают уже актуальный кэш, ничего заново не запрашивают;
- проверка БД - при каждом вызове делает реальный live-запрос (`SELECT 1`/ping): соединение может отвалиться независимо от состояния Discord;
- проверка Command Permissions API - при каждом вызове делает реальный REST-запрос (`GET /applications/{id}/guilds/{id}/commands/permissions`) заново, не полагаясь на локальный кэш от `APPLICATION_COMMAND_PERMISSIONS_UPDATE` - подстраховка на случай, если конкретное гейтвей-событие было пропущено (реконнект/разрыв) и кэш успел разойтись с реальным состоянием.

Разница между стартовым вызовом и `/healthcheck` только в этом: старт идёт против только что установленного соединения (кэш только формируется), команда - против уже прогретого кэша плюс два живых запроса (БД, Command Permissions API).

## Тик начисления опыта (Voices) - подход к реализации

Минутный тик по всем активным приватным комнатам (см. [components/Voices.md](components/Voices.md) "Тик начисления") - при неудачной реализации это два независимых источника лишней нагрузки: множество параллельных фоновых задач и частые точечные записи в БД. Требования к реализации:

- **Один центральный цикл, не по одному на комнату**: единый `tasks.loop(minutes=1)`, на каждой итерации проходящий по всему реестру активных комнат - не отдельная задача/таймер на каждую комнату.
- **Без обращений к Discord API**: тик читает только локальный кэш discord.py (войс-стейты участников, обновляемый гейтвей-событиями `on_voice_state_update` и т.п.) - `channel.members`, `.voice.self_deaf`/`.voice.deaf` и т.д.; никаких REST-запросов на подсчёт гостей не требуется.
- **Батчинг записи в БД**: очки накапливаются в памяти за тик и сбрасываются одним batch-запросом по всем комнатам разом; для комнат с нулевым приростом за тик (нет гостей / все исключены) запись в БД не делается вовсе.

Наблюдаемое поведение (кто сколько получает очков и когда) не меняется - см. [components/Voices.md](components/Voices.md), это только про то, как тик реализован под капотом.

## Логирование

- Единый логгер (`logging`, не `print`) с уровнями INFO/WARNING/ERROR.
- Стартовая диагностика: успешные проверки - INFO, ошибки - WARNING (модуль отключён, бот жив) или ERROR (критично, бот не поднялся) по правилам раздела выше.
- Рантайм-ошибки (не при старте) - тот же логгер, уровень ERROR, с контекстом (команда, вызвавший, цель) - привязанным к тому, что бот пытался сделать, не голый traceback.

## Валидация конфигурации

Все обязательные поля `.env` и per-module конфиги ([environment.md](environment.md) "Конфигурация") валидируются в одной точке при старте, до подключения к Discord:
- при отсутствии/некорректном значении - единый список всех проблем сразу (не первая попавшаяся), процесс завершается с ненулевым кодом;
- типизация: ID - целые числа (Discord snowflake), диапазоны/лимиты модулей (`60s–28d` для mute, `100` для бан-листа Voices, `300` для purge и т.д.) проверяются здесь же, при старте.
