# Окружение и деплой

> Стек, зависимости, права бота на живом сервере, устойчивость к рестарту, структура конфигурации - то, на чём и с чем работает бот. Что бот **делает** - см. [base.md](base.md) и [components/*.md](components/); сквозные правила, общие сразу для нескольких модулей - см. [rules.md](rules.md); требования к качеству кода (тесты, стартовая диагностика, логирование, валидация конфига) - см. [development.md](development.md).

## Технический стек
- **Single-guild**: бот жёстко заточен под один конкретный сервер, не рассчитан на работу на нескольких серверах одновременно. ID сервера - фиксированная часть `.env`.
- **Часовой пояс отображаемых дат - MSK (UTC+3), фиксированно**, не зависит от таймзоны VPS/ОС и не подстраивается под зрителя. Относится ко всем текстовым (не Discord-нативным) датам-строкам, форматируемым самим ботом - например, "Дата добавления" в [components/anti.md](components/anti.md), "Дата регистрации"/"Дата присоединения" в [components/roleGiver.md](components/roleGiver.md).
- Язык: Python.
- **Discord-библиотека: `discord.py` (актуальная 2.x ветка)**. Решение принято после полного описания функционала, с учётом масштаба сервера (единственная гильдия, ~200 000 участников, 80+ каналов/веток/форумов):
  - **Hybrid commands** (`commands.hybrid_command`) - одна функция-обработчик и одна проверка прав (`app_commands.check`) одновременно и для `/команда`, и для `!команда`, без дублирования логики; это же снимает риск рассинхрона при репликации Command Permissions на префиксный путь (см. [rules.md](rules.md) "Роли и права").
  - Шардинг Discord Gateway тут неактуален - он зависит от общего числа гильдий бота (~1 шард на 2500 гильдий); бот на единственном сервере всегда работает на одном шарде независимо от числа участников.
  - Реальная нагрузка от масштаба (память под кэш участников/войс-стейтов, пропускная способность `on_message` по 80+ каналам для [components/moderationChat.md](components/moderationChat.md), рейт-лимиты API) управляется через `discord.MemberCacheFlags` (не кэшировать участников целиком - только войс-стейты и роли) и архитектуру обработчиков (не блокировать `on_message`, тяжёлую работу - в очередь/таску).
  - Privileged intents (Guild Members, Message Content) нужны в любом случае из-за скана сообщений и проверки иерархии/дат аккаунта - верификация Discord для них требуется только у ботов на 100+ серверах, для одиночного кастомного сервера просто включаются вручную в Developer Portal.
  - Всё остальное закрывается штатными средствами библиотеки: `guild.audit_logs(action_type=...)` для наблюдения за ручными изменениями роли "работяга" ([components/anti.md](components/anti.md)), `on_raw_reaction_add` для очереди `!give` (переживает рестарт, не зависит от message-кэша, см. [components/roleGiver.md](components/roleGiver.md)), `on_voice_state_update` для [components/Voices.md](components/Voices.md), нативная поддержка Discord timeout для [components/mute.md](components/mute.md).
- Веб-панель управления не нужна - вся конфигурация через Discord (команды/роли/каналы) и файлы конфига бота.
- Хранилище данных: внутренняя БД бота - список "анти-работяг" ([components/anti.md](components/anti.md)), заявки `!give` на ручной проверке ([components/roleGiver.md](components/roleGiver.md)), реестр приватных войс-комнат + недельный опыт + персональные бан-листы владельцев комнат ([components/Voices.md](components/Voices.md)), overwrite'ы "предложки", проставленные ботом ([components/check.md](components/check.md)). Компоненты без своего состояния (mute, banKick, purge, moderationChat, antiBot) обходятся Discord-нативными механизмами или конфиг-файлом, БД им не нужна - см. по каждому компоненту.

## Права бота на сервере
**У бота НЕТ права Administrator.** Вместо этого выдан конкретный, курируемый набор прав - этот набор является **потолком**: ни одному модулю не может требоваться право, которого нет в этом списке, а обратное (право есть в списке, но пока ни один модуль его не использует) - не ошибка, просто резерв на будущее.

Список: `Manage Server`, `Manage Roles`, `Manage Channels`, `Kick Members`, `Ban Members`, `Create Invite`, `Manage Nicknames`, `Change Nickname`, `Manage Webhooks`, `View Audit Log`, `View Channels`, `Manage Events`, `Create Events`, `Moderate Members` (timeout - в интерфейсе Discord подписан не буквальным "Тайм-аут участников", а "Отправить участников подумать о своём поведении"), `View Server Insights`, `Send Messages`, `Send Messages in Threads`, `Create Public Threads`, `Create Private Threads`, `Manage Threads`, `Manage Messages`, `Read Message History`, `Embed Links`, `Attach Files`, `Use External Emojis`, `Mention Everyone/Here/All Roles`, `Add Reactions`, `Use External Stickers`, `Use Application Commands`, `Create Polls`, `Bypass Slowmode` (нужно в `#выдача-работяг` - медленный режим канала не должен задерживать ответы бота на `!give`, см. [components/roleGiver.md](components/roleGiver.md)), `Connect`, `Speak`, `Mute Members`, `Deafen Members`, `Move Members`, `Use Voice Activity`, `Priority Speaker`, `Request to Speak`, `Video`, `Use Activities`, `Use External Sounds`.

Явно **не выдано**: `Administrator`, `Manage Expressions`, `Create Expressions`, `View Server Subscription Insights`, `Use External Apps`, `Send Voice Messages`, `Pin Messages`, `Manage Official Messages` (webhook/announcement-related), `Use Soundboard`, `Set Voice Channel Status`.

Отсутствие `Administrator` не мешает проверке иерархии ролей - см. [rules.md](rules.md) "Роли и права". Роль бота на сервере намеренно расположена так, чтобы бот мог модерировать всех участников.

## Развёртывание и устойчивость к рестарту
Бот работает как сервис на Linux под `systemctl` - должен уметь автоматически перезапускаться при падении/перезагрузке сервера и **продолжать** работу. Это обязательное требование, конкретно затрагивает минимум два модуля:
- **Voices** ([components/Voices.md](components/Voices.md)): накопленный за неделю счёт опыта и точка отсчёта недельного цикла должны переживать рестарт - иначе рестарт посреди недели обнулит прогресс всех комнат.
- **roleGiver** ([components/roleGiver.md](components/roleGiver.md)): заявки на ручную проверку `!give` могут висеть до суток и дольше в ожидании реакции модератора - если бот перезапустится в этот момент, он всё равно должен корректно принять и обработать реакцию, поставленную после рестарта.

Общий принцип: любое состояние, которое живёт дольше одного запроса/тика и на которое может повлиять рестарт, должно быть персистентным (БД).

Дополнительные моменты, специфичные для падения/рестарта (не просто планового перезапуска):
- **Незавершённые многошаговые операции.** Некоторые команды делают несколько раздельных действий подряд (например, `/add` - снимает роль в Discord И пишет в БД). Атомарно связать действие в Discord API и запись в свою БД нельзя, поэтому при падении ровно между шагами возможна рассинхронизация. Устраняется уже заложенными механизмами реконсиляции (см. [components/mute.md](components/mute.md), [components/check.md](components/check.md)), не транзакционностью.
- **Пропущенное время простоя не восстанавливается ретроактивно, включая ролевые события.** Discord gateway не присылает события, случившиеся, пока бот был offline - значит, сообщения с подозрительными словами/медиа за это время не попадут в чек-листы ([components/moderationChat.md](components/moderationChat.md)), тик опыта в войсах ([components/Voices.md](components/Voices.md)) за это время просто не начислится никому, а ручные изменения роли "работяга" ([components/anti.md](components/anti.md)) во время простоя останутся незамеченными. Это принимаемое ограничение: бот на старте не сверяется с журналом аудита Discord за пропущенное время.
- **systemd-юнит**: `Restart=on-failure` с ненулевым `RestartSec` и ограничением `StartLimitBurst`/`StartLimitIntervalSec`, чтобы падение сразу при старте (битый `.env`, недоступна БД) не создавало busy-loop мгновенных рестартов и риск рейт-лимита на токен бота.

## Конфигурация
Два разных уровня конфигурации, разделённые по назначению:

1. **`.env`** - всё, без чего бот физически не может работать: ID сервера, ID каналов, ID ролей (в т.ч. те, которыми бот сам управляет - "работяга", "Молчун", "Душа компании"), токен бота и т.п.
2. **Конфиг-файл на уровне каждого модуля** - лимиты, пороги и прочие "тюнинговые" константы, привязанные конкретно к своему модулю, каждый в собственном файле. Например:
   - модуль **mute** - диапазон `60s–28d`, ссылка "Правила сервера" для DM-шаблонов (см. [components/mute.md](components/mute.md));
   - модуль **roleGiver** - пороги ручной проверки: "меньше 2 недель на сервере", "аккаунт младше 6 месяцев", "меньше 20 минут между регистрацией и присоединением" (см. [components/roleGiver.md](components/roleGiver.md));
   - модуль **Voices** - очки за тик (`+8`/`+10`/`+5`), периодичность тика (1 минута), периодичность сброса/перевыдачи роли (1 неделя), лимит личного бан-листа владельца (100 записей) (см. [components/Voices.md](components/Voices.md));
   - модуль **moderationChat** - список подозрительных/плохих слов для критерия "слова", список доменов GIF-провайдеров для критерия "медиа" (см. [components/moderationChat.md](components/moderationChat.md));
   - модуль **purge** - мягкий лимит **300** сообщений за вызов (см. [components/purge.md](components/purge.md)).
