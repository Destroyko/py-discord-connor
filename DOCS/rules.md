# Общие правила

> Правила и проверки, которые действуют одинаково сразу в нескольких модулях - не логика конкретной команды, а сквозные инварианты: иерархия ролей, самомодерация, гонки одинаковых команд, поведение при выходе/повторном входе на сервер, видимость ответов, обработка команд в ЛС. Что делает каждый конкретный модуль - см. [base.md](base.md) и [components/*.md](components/).

## Роли и права
- **Иерархия ролей модерации не задаётся отдельным конфигом бота** - берётся напрямую из штатного порядка ролей Discord (то, что в библиотеке обычно доступно как позиция роли/`top_role.position` и т.п.). Это единый список позиций для ВСЕХ ролей сервера подряд, включая роли ботов - оттуда же и сравнение "цель выше/равна инициатору", и определение, что цель - бот.
- Проверка иерархии применяется только к одному правилу: нельзя выдать наказание (мут/бан/кик/снятие роли и т.п.) пользователю, чья топовая роль выше или равна топовой роли инициатора команды (см. пример текста ошибки в [mute.md](components/mute.md)).
- **Самомодерация**: для `/mute`, `/ban`, `/kick` цель = сам инициатор команды проверяется отдельным явным правилом (а не проверкой иерархии, хотя формально своя роль всегда равна своей) и отвечает отдельным текстом - `Что ты делаешь?` (см. таблицы ошибок в [mute.md](components/mute.md), [banKick.md](components/banKick.md)). Для `/unban` и `/unmute` отдельная проверка на самомодерацию не нужна - случай покрывается сам по себе: если инициатор реально забанен/замьючен, он физически не может вызвать команду бота (бан удаляет с сервера; таймаут блокирует использование команд бота); если не забанен/не замьючен - цель на себя просто попадает в обычную ошибку "не найден в списке банов"/"не в муте" (см. [mute.md](components/mute.md), [banKick.md](components/banKick.md)), без специального текста про самомодерацию.
- **Владелец сервера как цель**: Discord API сам отклоняет попытки timeout/kick/ban против владельца гильдии независимо от ролей - это защита на уровне Discord (не бота), и сравнение позиций ролей её не гарантирует (у владельца может не быть специальной роли вообще). Бот должен **явно** проверять `target.id == guild.owner_id` как часть проверки иерархии (наравне со сравнением позиций и проверкой "цель - бот"), чтобы не полагаться на падение API-вызова, и при срабатывании отвечать тем же текстом отказа, что и при обычном нарушении иерархии для этой команды (см. пример в [mute.md](components/mute.md)) - отдельного, специального сообщения для этого случая не предусмотрено.
- Доступ к самим командам (кто вообще может вызвать `/mute`, `/add` и т.п., и в каких каналах) настраивается через встроенные Integrations → Command Permissions (зона видимости команды по каналам + требуемая роль) - это по-прежнему настройка сервера (не конфига бота), и при разворачивании аналога её нужно будет заново сделать через штатный интерфейс Discord.
- **Важное уточнение**: Command Permissions здесь - это конкретно экран Discord Integrations → (выбранное приложение) → команда → "Изменить права на использование команд": отдельная сущность **именно для slash-команд**, с переопределениями по ролям и по каналам на уровне конкретной команды (например, `/add` разрешена только в канале "антиработяги"). Это **не то же самое**, что обычные channel permission overwrites, которые бот сам расставляет на каналах (см. [check.md](components/check.md)) - это отдельный, application-command-specific слой прав, видимый только в настройках интеграции бота.
- Эта механика физически не распространяется на префиксные команды (`!mute` и т.п.) - это просто текстовые сообщения, которые бот разбирает сам, Discord их никак не фильтрует через этот экран. Если `/команда` выключена в канале через этот экран, `!команда`-аналог в этом же канале тоже не срабатывает - бот **молча игнорирует** вызов, без ответа об ошибке прав. Значит бот **обязан сам проверять** те же ограничения для префиксного пути - точный механизм (через какой API и как реплицировать приоритет Discord) см. в [development.md](development.md).
- ID каналов и категорий, которыми пользуется бот (см. [base.md](base.md) "Каналы, завязанные на бота"), хранятся в `.env` - это отдельная категория от command permissions.
- Курируемый список прав, реально выданных роли бота на сервере (без `Administrator`) - см. [environment.md](environment.md) "Права бота на сервере". Отсутствие `Administrator` **не мешает** проверке иерархии ролей - она сравнивает позиции ролей ЦЕЛИ и ИНИЦИАТОРА команды между собой, независимо от позиции или прав бота.
- **Гонка одинаковых команд на одну цель**: если два наказания одного типа почти одновременно вызваны разными модераторами на одного и того же пользователя - побеждает тот запрос, что реально применился первым. Поведение для проигравшего запроса определяется конкретной командой: `anti`/`banKick` отвечают явной ошибкой "уже в списке"/"уже в бане" (см. [anti.md](components/anti.md), [banKick.md](components/banKick.md)). `mute` использует отдельный механизм - 60-секундную резервацию за автором первого наложения, см. [mute.md](components/mute.md) "Резервация после наложения мута" (нужен именно там, так как `/mute` в остальных случаях не отклоняет повторный вызов, а обновляет мут). Правило про "такие же" ограничено одинаковым типом команды на одного и того же пользователя - не любыми параллельными командами вообще.

## Поведение при выходе / повторном входе на сервер
Discord снимает **все** роли пользователя при выходе с сервера - это штатное поведение самого Discord, не специфика бота. Отсюда следствия для каждой части системы:
- **Роль "работяга"** - слетает. После повторного входа нужно заново вызвать `!give` (см. [roleGiver.md](components/roleGiver.md)).
- **Роль "Молчун"** - тоже слетает вместе со всеми ролями. Но **Discord timeout переживает выход/вход** (это модерационная запись на уровне пары пользователь-сервер, не членства) - при повторном входе замьюченного пользователя таймаут продолжает действовать, даже если роль-индикатор пропала. Требуется реконсиляция при `on_member_join`, см. [mute.md](components/mute.md).
- **Статус "анти-работяга"** - не слетает, хранится в БД бота как самостоятельная запись, не как роль/состояние Discord-членства. Переживает любой перерыв в членстве на сервере, снимается только явным `/del` (или ручной выдачей роли анти-работяге, см. [anti.md](components/anti.md)).
- **Роль "Душа компании"** - переустанавливается еженедельно самим ботом по свежему расчёту, так что вопрос "переживает ли выход" для неё не так актуален - при выходе текущего обладателя роль просто исчезнет вместе с остальными, а на следующем еженедельном пересчёте будет выдана заново тому, кто лидирует на тот момент.
- **Личный бан-лист приватного войса** ([Voices.md](components/Voices.md#управление-своим-голосовым-каналом-самомодерация-владельца)) - хранится в БД бота (аналогично анти-статусу), не привязан к текущему членству: сохраняется за id владельца, даже если сам владелец комнаты выходит с сервера и заходит заново.

## Видимость ответов команд (публичные vs личные)
**Общее правило**: ответы всех команд - обычные публичные сообщения в канале вызова, видимые всем. Ephemeral-ответы (личные, видны только вызвавшему) - механика, доступная **только** slash-командам; префиксные (`!команда`) физически не могут быть личными, любое сообщение бота в ответ на них видно всем в канале. Поскольку slash- и префиксная версия одной команды должны вести себя одинаково, по умолчанию ни одна команда не делается ephemeral - иначе поведение `/team` и `!team` разошлось бы.

Исключения:
- **`/ban_list`** ([Voices.md](components/Voices.md#управление-своим-голосовым-каналом-самомодерация-владельца)) - сам список всегда уходит в ЛС, независимо от способа вызова (это не ephemeral-механика, а осознанная отправка личного сообщения); в месте вызова дополнительно приходит короткое публичное подтверждение (или ошибка, если ЛС закрыты).
- **DM-уведомления при муте/анмуте** ([mute.md](components/mute.md)) - отдельный канал коммуникации (ЛС пользователю), не реплай на команду.
- **`/vkick`, `/vreturn`** ([Voices.md](components/Voices.md#управление-своим-голосовым-каналом-самомодерация-владельца)) - ответ личный (ephemeral) для slash-варианта; для префиксного `!vkick`/`!vreturn` - публичный (ограничение Discord).

Все остальные команды (`mute`/`unmute`, `ban`/`kick`/`unban`, `add`/`del`, `check`, `give`, `ladder`, включая тексты ошибок валидации) - публичные, без исключений.

## Команды в личных сообщениях боту (DM)
По умолчанию бот **не обрабатывает** команды, отправленные ему в личные сообщения - ни slash, ни `!`-префиксные. Исключение - ровно две пользовательские команды приватных войсов, рассчитанные по смыслу и на вызов из ЛС, обе только в префиксной форме: `!vdel <id>` и `!ban_list` (у обеих нет slash-варианта с DM-контекстом - лишние публичные регистрации команд под ЛС не заводятся, см. [Voices.md](components/Voices.md#управление-своим-голосовым-каналом-самомодерация-владельца)). Slash-вариант `/ban_list` в ЛС не работает - только внутри гильдии, как и все остальные команды бота.

- **Slash-команды**: все, без исключений, регистрируются как guild-only (контекст выполнения ограничен сервером) - Discord сам не даёт вызвать их в ЛС, боту не нужно проверять это в коде.
- **Префиксные команды**: в ЛС Command Permissions Discord не действуют (это slash-only механика, см. "Роли и права" выше) - бот обязан сам проверять контекст сообщения (`message.guild is None`) и молча игнорировать любую `!`-команду в ЛС, кроме `!vdel` и `!ban_list`.
