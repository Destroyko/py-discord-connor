# Бот Коннор — обзорная документация

> Статус: реверс-инжиниринг по памяти автора (владелец сервера/модератор), доступа к исходному коду/БД оригинала нет. Всё, что не подтверждено наблюдением, помечено как открытый вопрос.

## Назначение
Бот для управления Discord-сервером в помощь модераторам: наказания, роли, контроль голосовых и текстовых чатов, логирование действий.

## Технический стек
- **Single-guild**: бот жёстко заточен под один конкретный сервер, не рассчитан на работу на нескольких серверах одновременно. ID сервера — часть `.env`, а не динамически определяемый параметр.
- Язык: Python (подтверждено).
- **Discord-библиотека: `discord.py` (актуальная 2.x ветка)**. Решение принято после полного описания функционала, с учётом масштаба сервера (единственная гильдия, ~200 000 участников, 80+ каналов/веток/форумов):
  - **Hybrid commands** (`commands.hybrid_command`) — одна функция-обработчик и одна проверка прав (`app_commands.check`) одновременно и для `/команда`, и для `!команда`, без дублирования логики; это же снимает риск рассинхрона при репликации Command Permissions на префиксный путь (см. "Роли и права" выше).
  - Шардинг Discord Gateway тут неактуален — он зависит от общего числа гильдий бота (~1 шард на 2500 гильдий), а не от размера одной гильдии; бот на единственном сервере всегда работает на одном шарде независимо от числа участников.
  - Реальная нагрузка от масштаба (память под кэш участников/войс-стейтов, пропускная способность `on_message` по 80+ каналам для [moderationWords.md](components/moderationWords.md)/[moderationMedia.md](components/moderationMedia.md), рейт-лимиты API) управляется через `discord.MemberCacheFlags` (не кэшировать участников целиком — только войс-стейты и роли) и архитектуру обработчиков (не блокировать `on_message`, тяжёлую работу — в очередь/таску), а не выбором библиотеки как таковым.
  - Privileged intents (Guild Members, Message Content) нужны в любом случае из-за скана сообщений и проверки иерархии/дат аккаунта — верификация Discord для них требуется только у ботов на 100+ серверах, для одиночного кастомного сервера просто включаются вручную в Developer Portal.
  - Всё остальное закрывается штатными средствами библиотеки: `guild.audit_logs(action_type=...)` для [eventWatcher.md](components/eventWatcher.md), `on_raw_reaction_add` для очереди `!give` (переживает рестарт, не зависит от message-кэша, см. [roleGiver.md](components/roleGiver.md)), `on_voice_state_update` для [Voices.md](components/Voices.md)/[voiceOwner.md](components/voiceOwner.md), нативная поддержка Discord timeout для [mute.md](components/mute.md).
  - Альтернатива, которую рассматривали и отклонили: **Hikari** (+ Lightbulb/Arc) — ничего не кэширует по умолчанию, потенциально экономнее по памяти именно под такой крупный одиночный сервер, но экосистема/документация/комьюнити несравнимо меньше — при чисто документационном, поддерживаемость-ориентированном процессе разработки этого проекта discord.py — более безопасный выбор.
- Команды: поддерживаются одновременно **slash-команды** (`/mute`) и **префиксные** (`!mute`, префикс `!`).
- Веб-панель управления не нужна — вся конфигурация через Discord (команды/роли/каналы) и файлы конфига бота.
- Хранилище данных: внутренняя БД бота (минимум для списка "анти-работяг", см. [anti.md](components/anti.md); вероятно используется и для других компонентов — уточняется по ходу описания каждого).
- Конфигурация через `.env`: ID ролей, которыми бот сам управляет (выдаёт/снимает) — **"работяга", "Молчун", "Душа компании"**. Роли, которые лишь ПРОВЕРЯЮТСЯ (например, донат-роль, дающая доступ в "предложку"), боту знать не нужно — доступ определяется через эффективные права канала (`channel.permissions_for(member)` или аналог), а не через список конкретных ролей.

## Роли и права
- **Иерархия ролей модерации не задаётся отдельным конфигом бота** — берётся напрямую из штатного порядка ролей Discord (то, что в библиотеке обычно доступно как позиция роли/`top_role.position` и т.п.). Это единый список позиций для ВСЕХ ролей сервера подряд, включая роли ботов — оттуда же и сравнение "цель выше/равна инициатору", и определение, что цель — бот.
- Проверка иерархии применяется только к одному правилу: нельзя выдать наказание (мут/бан/кик/снятие роли и т.п.) пользователю, чья топовая роль выше или равна топовой роли инициатора команды (см. пример текста ошибки в [mute.md](components/mute.md)). Самомодерация (цель = сам инициатор) автоматически блокируется этим же правилом — своя роль всегда равна своей.
- **Владелец сервера как цель**: Discord API сам отклоняет попытки timeout/kick/ban против владельца гильдии независимо от ролей — это защита на уровне Discord, а не бота, и сравнение позиций ролей её не гарантирует (у владельца может не быть специальной роли вообще). Бот должен **явно** проверять `target.id == guild.owner_id` как часть проверки иерархии (наравне со сравнением позиций и проверкой "цель — бот"), чтобы не полагаться на падение API-вызова, и при срабатывании отвечать тем же текстом отказа, что и при обычном нарушении иерархии для этой команды (см. пример в [mute.md](components/mute.md)) — отдельного, специального сообщения для этого случая не предусмотрено.
- Доступ к самим командам (кто вообще может вызвать `/mute`, `/add` и т.п., и в каких каналах) настраивается через встроенные Integrations → Command Permissions (зона видимости команды по каналам + требуемая роль) — это по-прежнему настройка сервера, а не конфига бота, и при разворачивании аналога её нужно будет заново сделать через штатный интерфейс Discord.
- **Важное уточнение**: Command Permissions здесь — это конкретно экран Discord Integrations → (выбранное приложение) → команда → "Изменить права на использование команд": отдельная сущность **именно для slash-команд**, с переопределениями по ролям и по каналам на уровне конкретной команды (например, `/add` разрешена только в канале "антиработяги"). Это **не то же самое**, что обычные channel permission overwrites, которые бот сам расставляет на каналах (см. [check.md](components/check.md)) — это отдельный, application-command-specific слой прав, видимый только в настройках интеграции бота.
- Эта механика физически не распространяется на префиксные команды (`!mute` и т.п.) — это просто текстовые сообщения, которые бот разбирает сам, Discord их никак не фильтрует через этот экран. **Подтверждено на оригинале**: если `/команда` выключена в канале через этот экран, `!команда`-аналог в этом же канале тоже не срабатывает — бот **молча игнорирует** вызов, без ответа об ошибке прав. Значит бот **обязан сам проверять** те же ограничения для префиксного пути.
- **Технически это не требует ручного дублирования конфига.** Discord отдаёт эту конфигурацию через API — `GET /applications/{application_id}/guilds/{guild_id}/commands/permissions` (работает на обычном bot-токене), и присылает live-обновления через gateway-событие `APPLICATION_COMMAND_PERMISSIONS_UPDATE` при каждом изменении на сервере. Бот должен вычитать эту конфигурацию (при старте + держать в кэше, обновляемом по этому событию) и на её основе сам проверять `!`-вызовы — воспроизводя тот же приоритет, что использует сам Discord: базовое требование команды (`default_member_permissions`) → оверрайды по ролям → оверрайды по каналам (канал побеждает).
- В `.env` попадают только ID каналов, куда бот **сам** иногда должен писать проактивно (лог-каналы, чек-листы и т.п., см. "Конфигурация" ниже) — это отдельная категория от command permissions.
- У бота — права администратора на сервере, что не мешает проверке иерархии: она сравнивает позиции ролей ЦЕЛИ и ИНИЦИАТОРА команды между собой, а не позицию бота. Роль бота на сервере намеренно расположена так, чтобы бот мог модерировать всех участников и младший состав модераторов (подтверждено, отдельно настраивать/проверять в коде не нужно).
- **Гонка одинаковых команд на одну цель**: если два наказания одного типа (например, два `/mute`) почти одновременно вызваны на одного и того же пользователя — принимается первый по времени запрос, остальные **тихо отклоняются** (без сообщения об ошибке). Правило про "такие же" — это одинаковый тип команды на одного и того же пользователя, а не любые параллельные команды вообще.

## Развёртывание и устойчивость к рестарту
Бот работает как сервис на Linux под `systemctl` — должен уметь автоматически перезапускаться при падении/перезагрузке сервера и **продолжать** работу, а не начинать заново. Это требование, а не просто пожелание — конкретно затрагивает минимум два модуля:
- **Voices** ([Voices.md](components/Voices.md)): накопленный за неделю счёт опыта и точка отсчёта недельного цикла должны переживать рестарт — иначе рестарт посреди недели обнулит прогресс всех комнат.
- **roleGiver** ([roleGiver.md](components/roleGiver.md)): заявки на ручную проверку `!give` могут висеть до суток и дольше в ожидании реакции модератора — если бот перезапустится в этот момент, он всё равно должен корректно принять и обработать реакцию, поставленную после рестарта.

Общий принцип: любое состояние, которое живёт дольше одного запроса/тика и на которое может повлиять рестарт, должно быть персистентным (БД), а не только в памяти процесса.

Дополнительные моменты, специфичные для падения/рестарта (не просто планового перезапуска):
- **Незавершённые многошаговые операции.** Некоторые команды делают несколько раздельных действий подряд (например, `/add` — снимает роль в Discord И пишет в БД). Атомарно связать действие в Discord API и запись в свою БД нельзя, поэтому при падении ровно между шагами возможна рассинхронизация. Рассчитываем на уже заложенные механизмы реконсиляции (см. [mute.md](components/mute.md), [check.md](components/check.md)), а не на транзакционность.
- **Пропущенное время простоя не восстанавливается ретроактивно.** Discord gateway не присылает события, случившиеся, пока бот был offline — значит, сообщения с банвордами/медиа за это время не попадут в чек-листы ([moderationWords.md](components/moderationWords.md), [moderationMedia.md](components/moderationMedia.md)), а тик опыта в войсах ([Voices.md](components/Voices.md)) за это время просто не начислится никому. Это принимаемое ограничение, а не то, что нужно "долечивать".
- **(Открытый вопрос) Догоняющая сверка через журнал аудита Discord при старте** — audit log хранится ограниченное время, теоретически можно на старте свериться с ним и найти пропущенные ручные действия модераторов (например, роль снята вручную, пока бот был выключен). Закрыло бы часть проблемы выше для ролевых событий, но не для форвардинга сообщений/тиков. Решение — делать или нет — пока не принято.
- **systemd-юнит**: `Restart=on-failure` с ненулевым `RestartSec` и ограничением `StartLimitBurst`/`StartLimitIntervalSec`, чтобы падение сразу при старте (битый `.env`, недоступна БД) не создавало busy-loop мгновенных рестартов и риск рейт-лимита на токен бота.

## Конфигурация
Два разных уровня конфигурации, разделённые по назначению:

1. **`.env`** — всё, без чего бот физически не может работать: ID сервера, ID каналов, ID ролей (в т.ч. те, которыми бот сам управляет — "работяга", "Молчун", "Душа компании", см. п. "Технический стек" выше), токен бота и т.п.
2. **Конфиг-файл на уровне каждого модуля** — лимиты, пороги и прочие "тюнинговые" константы, которые относятся конкретно к этому модулю, а не разбросаны по коду или свалены в один общий файл. Например:
   - модуль **mute** — диапазон `60s–28d` (см. [mute.md](components/mute.md));
   - модуль **roleGiver** — пороги ручной проверки: "меньше 2 недель на сервере", "аккаунт младше 6 месяцев" (см. [roleGiver.md](components/roleGiver.md));
   - модуль **Voices** — очки за тик (`+8`/`+10`/`+5`), периодичность тика (1 минута), периодичность сброса/перевыдачи роли (1 неделя) (см. [Voices.md](components/Voices.md));
   - модуль **voiceOwner** — лимит личного бан-листа (100 записей) (см. [voiceOwner.md](components/voiceOwner.md));
   - модуль **moderationWords** — список банвордов/подозрительных слов (см. [moderationWords.md](components/moderationWords.md)).

## Поведение при выходе / повторном входе на сервер
Discord снимает **все** роли пользователя при выходе с сервера — это штатное поведение самого Discord, не специфика бота. Отсюда следствия для каждой части системы:
- **Роль "работяга"** — слетает. После повторного входа нужно заново вызвать `!give` (см. [roleGiver.md](components/roleGiver.md)).
- **Роль "Молчун"** — тоже слетает вместе со всеми ролями. Но **Discord timeout переживает выход/вход** (это модерационная запись на уровне пары пользователь-сервер, а не членства) — при повторном входе замьюченного пользователя таймаут продолжает действовать, даже если роль-индикатор пропала. Требуется реконсиляция при `on_member_join`, см. [mute.md](components/mute.md).
- **Статус "анти-работяга"** — не слетает, хранится в БД бота, а не как роль/состояние Discord-членства. Переживает любой перерыв в членстве на сервере, снимается только явным `/del` (или ручной выдачей роли анти-работяге, см. [anti.md](components/anti.md)).
- **Роль "Душа компании"** — переустанавливается еженедельно самим ботом по свежему расчёту, так что вопрос "переживает ли выход" для неё не так актуален — при выходе текущего обладателя роль просто исчезнет вместе с остальными, а на следующем еженедельном пересчёте будет выдана заново тому, кто лидирует на тот момент.
- **Личный бан-лист приватного войса** ([voiceOwner.md](components/voiceOwner.md)) — хранится в БД бота (аналогично анти-статусу), не привязан к текущему членству напрямую, но открытым остаётся вопрос, что происходит, если сам ВЛАДЕЛЕЦ комнаты выходит и заходит заново (список, скорее всего, сохраняется за его id).

## Связи между модулями
Не монолит — модули делятся на кластеры по фактической связности данных/состояния:

**Независимые модули** (свой конфиг, свой канал, ни от кого не зависят):
- [moderationWords.md](components/moderationWords.md), [moderationMedia.md](components/moderationMedia.md) — полностью автономны.
- [antiBot.md](components/antiBot.md) — автономен (и вне скоупа).

**Кластер "работяга"** — общее состояние (анти-список):
- [anti.md](components/anti.md) — держит сам анти-список, это его состояние.
- [roleGiver.md](components/roleGiver.md) — читает анти-список при `!give`.
- [check.md](components/check.md) — читает анти-статус, управляет overwrite'ами в "предложке" как следствие анти-статуса.
- Все трое пишут события в [eventWatcher.md](components/eventWatcher.md).

**Кластер "приватные войсы"** — общая сущность "комната":
- [Voices.md](components/Voices.md) — создаёт комнаты, считает опыт.
- [voiceOwner.md](components/voiceOwner.md) — оперирует теми же комнатами (`/vkick` и т.д.), общий с Voices список "владелец → комната".
- Voices дополнительно читает состояние мута из [mute.md](components/mute.md) (исключение замьюченных из подсчёта опыта) — единственная межкластерная зависимость на чтение.
- **На этапе реализации** — несмотря на два файла документации, это одна сущность/один реестр комнат ("владелец → комната"), а не два независимых модуля. Реестр комнат должен быть общим (одна таблица/источник правды), config — тоже один на кластер (очки опыта + лимит бан-листа вместе, см. "Конфигурация" выше); Voices и voiceOwner — это два набора операций (фоновый тик+лидерборд / команды самомодерации) над одним и тем же реестром, а не два отдельных сервиса с своими копиями данных о комнатах.

**Базовая модерация** — используют общую утилиту проверки иерархии (см. "Роли и права" выше), но не зависят друг от друга:
- [mute.md](components/mute.md), [banKick.md](components/banKick.md).

**EventWatcher как сквозной сервис**: [eventWatcher.md](components/eventWatcher.md) сейчас формально знает про anti/roleGiver, потому что реагирует на конкретные их события ("сняли работягу", "решение по !give"). Для сервисной архитектуры логичнее развернуть это в обратную сторону — превратить eventWatcher в независимый слушатель общих событий ("роль снята X, кем Y", "решение принято X по Y"), которые публикуют другие модули, не зная деталей форматирования лога. Тогда добавление нового модуля с логированием не потребует правок в eventWatcher, и наоборот.

## Каналы, завязанные на бота
**Принцип конфигурации (по формату ответа)**: в `.env` попадают ID только тех каналов, куда бот пишет **проактивно** (по своей инициативе — не как прямой ответ на команду, вызванную в этом же канале). Если команда просто отвечает туда же, где её вызвали, боту не нужно отдельно хранить ID этого канала ради маршрутизации ответа — реплай идёт в контекст вызова автоматически. Отсюда ниже часть каналов помечена "боту знать не обязательно" — **но это только про маршрутизацию ответа**, не про авторизацию: независимо от этого бот должен читать полную конфигурацию Command Permissions через Discord API, чтобы реплицировать те же ограничения на префиксный (`!`) путь вызова — см. "Роли и права" выше.

- **`#реквесты-работяг`** — сюда бот **проактивно** публикует `@here`-запросы с реакциями ✅/❌ на ручную проверку `!give` (пользователь вызывает команду в `#выдача-работяг`, а запрос на модерацию уходит в другой канал) — бот обязан знать ID. См. [roleGiver.md](components/roleGiver.md).
- **`#бот-команды`** — канал вызова `mute`/`unmute`/`kick`, для этой роли боту знать ID не обязательно (он только отвечает в месте вызова). Но бот **обязан** знать этот ID отдельно: сюда же **проактивно** уходит embed-лог `!purge` (см. [purge.md](components/purge.md)) — команда вызывается в другом канале (вне модераторской категории), а лог пишется сюда независимо от места вызова. См. [mute.md](components/mute.md), [banKick.md](components/banKick.md).
- **`#антиработяги`** — канал команд `/add`/`/del`; сюда же бот **проактивно** пишет при возврате/изъятии роли "работяга" у анти-работяги, в том числе когда изменение сделано вручную через Discord UI (без команды) — бот обязан знать ID. См. [anti.md](components/anti.md), [eventWatcher.md](components/eventWatcher.md).
- **`#аудит`** — сюда бот **проактивно** пишет результат обработки заявки `!give` (кто из модераторов одобрил/отказал) — результат решения по реакции ✅/❌, а не прямой ответ на команду, поэтому бот обязан знать ID. См. [eventWatcher.md](components/eventWatcher.md).
- **`#выдача-работяг`** — единственное место вызова `!give` пользователем. См. [roleGiver.md](components/roleGiver.md).
- **`#баны`** — канал вызова `ban`/`unban`. Боту знать не обязательно — он только отвечает в месте вызова. См. [banKick.md](components/banKick.md).
- Каналы, связанные с приватными голосовыми комнатами (система "опыта", см. [Voices.md](components/Voices.md)) — существуют, детали в отдельном компоненте.
- **`#флудиславль`** — канал для команд управления собственным приватным голосовым каналом (`!vreturn @user`, см. [voiceOwner.md](components/voiceOwner.md)), для `!check` ([check.md](components/check.md)) и для еженедельного уведомления о перевыдаче роли "Душа компании" ([Voices.md](components/Voices.md)) — один и тот же канал во всех трёх случаях.
- **`#чек-лист`** — пересылка подозрительных по словам сообщений, см. [moderationWords.md](components/moderationWords.md).
- **`#чек-лист2`** — пересылка всех медиавложений, см. [moderationMedia.md](components/moderationMedia.md).
- **`#предложка`** — платный/ролевой чат, доступ в который дополнительно точечно блокируется для анти-работяг, см. [check.md](components/check.md).
- **ID модераторской категории "роддом"** (не отдельный канал, а категория целиком; включает как минимум `#антиработяги`, `#бот-команды`) — бот **обязан** знать этот ID: проверка на подозрительные слова/медиа/`!purge` пропускает любой канал внутри неё (сравнение по `channel.category_id`, а не список конкретных каналов), см. [moderationWords.md](components/moderationWords.md). Тредов/форум-топиков внутри этой категории нет — только обычные текстовые каналы.

## Видимость ответов команд (публичные vs личные)
**Общее правило**: ответы всех команд — обычные публичные сообщения в канале вызова, видимые всем. Ephemeral-ответы (личные, видны только вызвавшему) — механика, доступная **только** slash-командам; префиксные (`!команда`) физически не могут быть личными, любое сообщение бота в ответ на них видно всем в канале. Поскольку slash- и префиксная версия одной команды должны вести себя одинаково, по умолчанию ни одна команда не делается ephemeral — иначе поведение `/team` и `!team` разошлось бы.

Исключения:
- **`/ban_list`** ([voiceOwner.md](components/voiceOwner.md)) — ответ всегда уходит в ЛС, независимо от способа вызова (это не ephemeral-механика, а осознанная отправка личного сообщения).
- **DM-уведомления при муте/анмуте** ([mute.md](components/mute.md)) — отдельный канал коммуникации (ЛС пользователю), не реплай на команду.
- **`/vkick`, `/vreturn`** ([voiceOwner.md](components/voiceOwner.md)) — ответ должен быть личным (ephemeral) **для slash-варианта**. Для префиксного `!vkick`/`!vreturn` личный ответ невозможен технически (ограничение Discord) — там ответ неизбежно публичный в канале вызова. Это осознанное расхождение поведения между `/` и `!` версиями именно для этих двух команд.

Все остальные команды (`mute`/`unmute`, `ban`/`kick`/`unban`, `add`/`del`, `check`, `give`, `ladder`, включая тексты ошибок валидации) — публичные, без исключений.
Каждая модерационная/функциональная команда доступна и как слэш-, и как префиксная (`!`); у каждой настроены command permission overrides на сервере. Исключение — `!kiss` (см. ниже): только префиксная, без slash-варианта и без ограничений по каналам.

| Команда | Назначение (черновое) | Компонент | Статус |
|---|---|---|---|
| `/add <id>` | Добавить пользователя в список "анти-работяг" + забрать роль "работяга" | anti | Подтверждено |
| `/del <id>` | Убрать из списка "анти-работяг" + вернуть роль "работяга" | anti | Подтверждено |
| `/anti-bot` | Переключатель (вкл/выкл) авто-бана всех новых входящих на сервер — экстренная антирейд-защита | antiBot | **Не в скоупе разработки** — механика не до конца ясна, см. [antiBot.md](components/antiBot.md) |
| `/ban` | Забанить участника, embed-ответ (аналог `/kick`, не подтверждён отдельно) | banKick | Подтверждено направление, точный embed не подтверждён |
| `/ban_list` | Присылает вызвавшему в ЛС его личный список забаненных из СВОЕГО приватного войса (id + упоминание, до 100 записей), с инструкцией по снятию | voiceOwner | Подтверждено |
| `/check` | Проверяет доступ вызвавшего к чату "предложка" (анти-статус + роль + висящие ограничения) и чинит рассинхрон | check | Подтверждено |
| `/give` | Выдача роли "работяга" (с проверкой анти-списка) | roleGiver / anti | Подтверждено (частично) |
| `/kick <id> <reason>` | Кикнуть участника с сервера, причина обязательна | banKick | Подтверждено |
| `/ladder` | Уровень/опыт в приватных войсах | Voices | Подтверждено направление, детали уточняются |
| `/mute` | Выдать мут (роль "молчун" + таймаут Discord, текст+войс) | mute | Подтверждено |
| `/unmute` | Снять мут | mute | Подтверждено |
| `/vkick <id>` | Кикнуть пользователя из своего приватного войса + добавить в свой личный бан-лист (максимум 100 записей на владельца) | voiceOwner | Подтверждено |
| `/vreturn` | Снять ограничение (убрать из личного бан-листа) — `@user` в `#флудиславль`, либо `<id>` в ЛС с ботом | voiceOwner | Подтверждено |
| `!kiss` | Шуточная команда-пинг бота, без модерационной функции — ответ `Дядь, ты дурак?`. Без ограничений по каналам (command permissions для неё не настроены — работает в любом канале сервера). Только префиксная — slash-варианта `/kiss` нет | — (вне кластеров, не модерация) | Подтверждено |
| `!purge ...` | Массовое удаление сообщений (по количеству/автору/содержимому/типу вложения). Только префиксная, без модераторской категории, проверка права "Управлять сообщениями" | purge | Подтверждено, детали (embed-лог, точный лимит) уточняются |

**Живое подтверждение поведения из "Роли и права"**: на скриншоте автора `!ban <id>`, вызванный в канале, где `/ban` не разрешена через Command Permissions, не сработал — бот проигнорировал вызов, ответа не последовало; `!kiss`, вызванный следом в том же канале, сработал нормально — прямое наблюдение разницы между командой без ограничений и командой с channel-scoped Command Permissions.

**Исключено из скоупа:** функция "очистка чатов по команде модератора" (была п.7 в исходном списке возможностей) — уточнено у автора, что относится к ДРУГОМУ боту на сервере, к Коннору отношения не имеет. Убрано из документации и разработки. **Не путать** с `!purge` (см. [purge.md](components/purge.md)) — это отдельная, подтверждённая функция самого Коннора для массового удаления сообщений, добавлена в скоуп отдельно.

## Основные возможности (компоненты)
1. **Мут** по команде модератора — [mute.md](components/mute.md)
   - Механизм: отдельная роль "молчун" + параллельно стандартный Discord-таймаут. Действует и на текст, и на голос.
2. **Выдача/снятие роли** по команде модератора + автопроверка — [roleGiver.md](components/roleGiver.md)
3. **Слежение за голосовыми чатами**, начисление "опыта" в приватных войс-комнатах (создаваемых самими пользователями через бота), выдача роли за опыт — [Voices.md](components/Voices.md)
   - Отдельная механика от [roleGiver.md](components/roleGiver.md) (не пересекается по логике, но, возможно, использует ту же инфраструктуру выдачи роли).
4. **Слежение за текстовыми чатами**: пересылка подозрительных сообщений и медиафайлов в спец. чаты — [moderationWords.md](components/moderationWords.md), [moderationMedia.md](components/moderationMedia.md)
5. *(нумерация в исходном списке пропускает 5)*
6. **Логирование действий**: бан / выдача роли / снятие роли и т.п. — [eventWatcher.md](components/eventWatcher.md)
7. ~~Очистка чатов~~ — исключено, относится к другому боту сервера, не к Коннору.
8. **Управление своим голосовым каналом** (кикнуть кого-то, запретить заходить) — `/vkick`, `/vreturn`, `/ban_list` — [voiceOwner.md](components/voiceOwner.md)
9. **Anti (анти-работяга)** — не входит в исходную нумерацию 1–8, отдельная система контроля доступа к роли "работяга", медиа, стриму и чату "предложка" — [anti.md](components/anti.md), [check.md](components/check.md)
10. **Бан/кик** — базовая модерация — [banKick.md](components/banKick.md)
11. **Anti-Bot** — переключаемая экстренная защита от рейда ботов; **вне скоупа первой версии разработки** — [antiBot.md](components/antiBot.md)
12. **Purge** — не входит в исходную нумерацию 1–8, массовое удаление сообщений по команде модератора (`!purge`) — [purge.md](components/purge.md)
